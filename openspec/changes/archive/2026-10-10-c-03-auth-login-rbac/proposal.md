# Proposal — C-03 auth-login-rbac

## Why

C-02 dejó la identidad persistida (`usuario` con `username` único, `rol` ENUM, `password_hash` BCrypt(12), flag `activo`) pero sin forma de autenticar ni autorizar: `SecurityConfig` actual es `permitAll` parcial y `formLogin` sin `AuthenticationManager` ni `UserDetailsService`, no hay `POST /api/auth/login`, ni sesión/JWT, ni `403` por RBAC, ni rate limiting. Sin este change (GATE 2, camino crítico, governance **CRITICO**) todas las rutas de C-04..C-12 quedan expuestas a acceso anónimo o bypass por URL/API directa (viola RN-AU-01/02), y no existe sujeto autenticado para `created_by` ni para scoping Paciente/Odontólogo (RN-AU-03/04). `CHANGES.md` y `07 Flujo 6` congelan que login requiere validación bcrypt con mensaje genérico, rate limit 5/60s por `IP+username`, `GET /api/auth/me` y `POST /api/auth/logout`, middleware `AuthRequired` excepto `GET /`, `GET /login`, `POST /login`, `GET /api/health`, y redirección post-login por rol. Postergar auth propaga riesgo de seguridad a todo el roadmap y bloquea 3 changes paralelos de GATE 3.

## What Changes

- **Login API + form**: `POST /api/auth/login` (JSON) y `POST /login` (form, compat SSR) — valida `username`+`password` con `PasswordEncoder.matches` (BCrypt 12), rehuse de `UsuarioRepository.findByUsername`; si `activo=false` retorna 401 genérico; si credenciales inválidas 401 `{"error":"Credenciales inválidas"}` sin revelar existencia de usuario; en éxito crea sesión server-side y opcional cookie `JSESSIONID` `HttpOnly`/`Secure`/`SameSite=Lax`, o documenta alternativa JWT en `08` si se elige (este change elige **sesión server-side** ver Design D-01). Respuesta `LoginResponse {id, username, rol, email}`. Soporta `Accept: application/json` vs `form-urlencoded`.
- **Sesión server-side + endpoints**: `GET /api/auth/me` → `MeResponse {id, username, rol, email}` si autenticado, 401 si no; `POST /api/auth/logout` invalida sesión/`SecurityContext` y limpia cookie; `POST /api/auth/refresh` solo si se elige JWT (este change: no aplica, se deja como no-go y se documenta).
- **Rate limiting**: filtro `LoginRateLimitFilter` (`OncePerRequestFilter` + Bucket4j/caffeine in-memory) 5 intentos / 60s por clave `IP + username` normalizado (case-insensitive, `X-Forwarded-For` con `ForwardedHeaderFilter` + `server.forward-headers-strategy=native` detrás de proxy); al exceder 429 con `Retry-After` y body problem-details; no cuenta éxitos; reset en ventana deslizante.
- **AuthRequired / SecurityFilterChain**: endurece `SecurityFilterChain`: autoriza `permitAll` solo `GET /`, `GET /login`, `POST /login`, `POST /api/auth/login`, `GET /api/health`, `GET /actuator/health`, `GET /css/**`, `/js/**`, `/error`; `anyRequest().authenticated()`; `formLogin` con `loginPage("/login")`, `loginProcessingUrl("/login")`, `successHandler` que redirige por rol (`PACIENTE→/mis-turnos`, `ODONTOLOGO→/agenda`, `SECRETARIA/ADMIN→/agenda`) y `failureHandler` 401 JSON para API, 302 con `?error` para form; `sessionManagement` (`IF_REQUIRED`, max 1 sesión por usuario, `invalidSession` → login); CSRF habilitado para SSR (`CookieCsrfTokenRepository`) y headers CSP/`frameOptions sameOrigin`/`referrerPolicy NO_REFERRER`.
- **RBAC backend**: `@EnableMethodSecurity` ya activo; introduce `PermissionContext` / `AuthzService` con métodos `isOwner`, `hasAnyRole` y anotaciones `@PreAuthorize("hasRole('ADMIN')")` o `@PreAuthorize("@authz.isPacienteOwner(#id)")` aplicadas en controllers de C-04+ (en C-03 se prueba el mecanismo con endpoints `me/logout` y un `TestSecuredController`); checks RN-AU-02/03/04 en backend, nunca solo ocultando botón.
- **DTOs + validación**: `LoginRequest(@NotBlank username, @NotBlank password)`, `LoginResponse`, `MeResponse` con `from(Usuario)` mapper, nunca exponen `passwordHash`; `@Valid` en controller; `@ControllerAdvice` mapea `BadCredentialsException`/`DisabledException` → 401 genérico, `AccessDeniedException` → 403, `RateLimitExceeded` → 429, `MethodArgumentNotValid` → 400 con `fieldErrors` RFC7807 (`problemdetails.enabled=true` ya en C-01).
- **Tests**: login ok 200 + cookie + `me` ok, password incorrecto 401 genérico, usuario inactivo 401 genérico, ruta protegida sin sesión 302 (form) / 401 (API) según `Accept`, RBAC bypass por URL directa 403, rate limit 429 tras 5 fallos, logout invalida y `me` pasa a 401. Tests de integración con Testcontainers MySQL + `MockMvc` + `spring-security-test`.
- **No cambia**: tablas nuevas (usa `usuario` de C-02), ABM pacientes/profesionales/turnos (C-05..C-08), frontend agenda (C-11), JWT refresh si se mantiene sesión (documentado como fuera de alcance).

## Capabilities

### New Capabilities
- `auth`: Autenticación completa y RBAC por rol — login con validación bcrypt + rate limiting, sesión server-side `HttpOnly Secure SameSite=Lax`, endpoints `me`/`logout`, middleware AuthRequired (RN-AU-01), checks `PermissionContext`/`@PreAuthorize` (RN-AU-02/03/04), redirección por rol y DTOs `LoginRequest`/`LoginResponse`/`MeResponse`. Es el contrato observable de que solo usuarios autenticados acceden a recursos, que credenciales inválidas/inactivas responden 401 genérico, que rutas protegidas exigen sesión, y que RBAC por rol se hace cumplir en backend.

### Modified Capabilities
- _Ninguna_ — `platform-foundation` (health, env vars, BCrypt bean) y `user-accounts` (persistencia `Usuario`) quedan intactas; este change solo añade comportamiento `auth` sin redefinir requisitos de esas specs. Si validación futura exige endurecer `Seguridad base mínima`, se versionará allí; hoy no.

## Impact

- **Código nuevo**: `web/controller/AuthController.java` (+ `LoginController` para form si se separa), `application/dto/LoginRequest.java`, `LoginResponse.java`, `MeResponse.java`, `security/CustomUserDetailsService.java`, `security/CustomUserDetails.java`, `security/LoginRateLimitFilter.java` / `RateLimitService.java` (Bucket4j o `ConcurrentHashMap` + `Bucket`), `security/AuthzService.java` / `PermissionContext.java`, `security/SecurityJsonHandlers.java` (success/failure/accessDenied/authenticationEntryPoint), `config/SecurityConfig` modificado, `web/GlobalExceptionHandler` extendido (429).
- **Código modificado**: `SecurityConfig` (de `csrf.disable()`/`cors.disable()`/`formLogin` básico a config completa con CSRF `CookieCsrfTokenRepository`, headers CSP, `sessionManagement`, `authorizeHttpRequests` con lista cerrada de `permitAll`, `logout`, `exceptionHandling` JSON vs redirect); `application.properties` (`server.forward-headers-strategy=native` ya existe, se verifica; `app.login-rate-limit.*` opcionales); `TimeZoneConfig` sin cambio.
- **APIs**: `POST /api/auth/login` (JSON) + `POST /login` (form) → 200 `LoginResponse` + `Set-Cookie: JSESSIONID` o 401/429; `GET /api/auth/me` → 200 `MeResponse` o 401; `POST /api/auth/logout` → 204/200; `GET /login` → 200 HTML; `GET /`, `GET /api/health` permanecen públicos.
- **Dependencias**: `com.bucket4j:bucket4j-core` (o `bucket4j` + `caffeine`) si se adopta Bucket4j; ya existen `spring-boot-starter-security`, `spring-security-test`, `testcontainers:mysql`. Sin cambios de Flyway (`V2` intacta).
- **Sistemas**: Sesión en memoria (o `spring-session` futuro); rate limit in-memory por instancia (suficiente P0-scale:a single instance; para H-A se migraría a Redis). Secrets via `${APP_SECRET}`; CSRF token en cookie `XSRF-TOKEN` para SSR.
- **Riesgos si se omite**: Acceso anónimo a agenda/datos de pacientes (RGPD/PII), bypass RBAC por `curl` directo, brute force sin throttling, y bloqueo de todo GATE 3 (C-04/C-05/C-06 no pueden probar autorización).
- **Breaking**: ninguno para consumidores externos (no había auth antes); `anyRequest().authenticated()` endurece acceso — clientes sin sesión que antes recibían 200 ahora reciben 401/302, que es el comportamiento esperado por RN-AU-01.
- **Governance CRITICO**: requiere revisión de manejo de 401 genérico (no enumeración de usuarios), `HttpOnly`/`Secure`/`SameSite` en cookie, rate limit por IP+username con `ForwardedHeaderFilter`, `@PreAuthorize` deny-by-default, y tests de 403 bypass antes de merge.
